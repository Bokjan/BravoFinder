# 航路查找的基础算法：从最短路到 K 条候选

> **面向不熟悉图算法的读者。** 如果你想先弄明白「BravoFinder 到底怎么找出一条航路」，从这篇读起。后面的专题（合规约束、程序建模、性能）都建立在这里的概念上。相关代码：`libs/engine/core/graph/`（`nav_graph.h`、`astar.*`、`yen_kshortest.*`）。

## 1. 把空域看成一张「图」

计算机眼里，航路网就是一张 **图（graph）**：

- **顶点（vertex）**：一个个导航点——航路点（waypoint）、导航台（VOR/DME/NDB）。
- **边（edge）**：连接两个相邻导航点的一段航路，边上标着这段的**长度**（大圆距离，海里）。

于是「从 A 机场飞到 B 机场」就变成一个经典问题：**在这张图上，从起点走到终点，怎么走总距离最短？** 这就是 **最短路径（shortest path）** 问题。

> BravoFinder 的图用一种叫 **CSR（Compressed Sparse Row，压缩稀疏行）** 的紧凑结构存（`nav_graph.h`）：所有边挤在一个连续数组里，每个顶点记一段区间。好处是内存连续、遍历快、也方便直接存进缓存文件。对理解算法，你只需知道「它就是一张能高效遍历的图」。

## 2. 最短路的经典解法：Dijkstra

最经典的最短路算法是 **Dijkstra**：从起点出发，像水波一样一圈圈往外扩散，总是优先扩展「目前已知代价最小」的顶点，直到碰到终点。它保证找到真正的最短路，但有个缺点——它**没有方向感**，向终点、背离终点的方向一视同仁地扩散，会探索很多明显没用的顶点。

BravoFinder 的 v1/v2 就是用 Dijkstra.v3 换成了更快的 **A\***。

## 3. A\*：给 Dijkstra 装上「指南针」

**A\***（读作 A-star）在 Dijkstra 基础上加一个**启发函数（heuristic）** `h(v)`——对每个顶点估计「从这里到终点大概还有多远」。扩展顶点时，A* 不只看「已经走了多远」（记作 `g`），还加上「估计还要走多远」（`h`），按 `f = g + h` 排序优先扩展。这就像给扩散装了指南针：朝终点方向的顶点 `h` 小、更早被扩展，背离终点的被推后。**同样找到最短路，但少探索很多顶点。**

BravoFinder 的启发函数用**单位球弦长**（chord length）：把地球近似成单位球，把当前顶点和每个终点都先化成单位向量，启发值取「顶点到任一终点单位向量之差的模长」乘地球半径（`astar.cc` 的 `MultiGoalHeuristic`：`kEarthRadiusNm * |unit(v) - unit(g)|`）。

**关键性质：admissible（不高估），且比大圆距离更省。** 弦长是大圆弧长在弦上的投影，**恒 ≤ 弧长**，所以它仍是真实剩余距离的有效下界——实际沿航路飞只会更长、不会更短，因此 `h(v)` 永远不会高估，A* 必然找到真正的最优解。那为什么不直接用更精确的大圆（haversine）距离？因为 haversine 要算 `atan2` + `sin`/`cos`，在 k=10 的查询里每个 spur 都要对全部终点重复扫描一遍（perf 显示启发函数曾占约 34% 自耗时）；弦长把「角度」换成「向量差模长」——终点单位向量整轮 Yen 只预算一次、每个顶点的单位向量借 memo 每顶点只算一次，热路径里彻底没了 `atan2`。实测 k=10 从约 4.9ms 降到约 4.1ms（见 [performance.zh-CN.md](performance.zh-CN.md) 的 +chord / G2 档）。下界变松一点，但最优解不变，省下的是实打实的 CPU。

> 软代价怎么办？后面「合规约束」会讲到某些边有额外惩罚代价。因为惩罚只会让路更「贵」、不会让地理距离变短，弦长下界**仍然**成立，A* 在惩罚后的代价下依然最优。详见 [compliant-routing.zh-CN.md](compliant-routing.zh-CN.md)。

## 4. 为什么只要一条最短路还不够

现实里，「最短的那一条」未必是你想要的：

- 它可能擦着某个高度/方向约束的边界，换一条稍长的更稳妥；
- 换一个 SID/STAR 衔接点、走另一条平行航路，可能更顺；
- 你可能就想看看「还有哪些走法」，自己挑。

所以 BravoFinder 不只给一条，而是给 **前 K 条候选航路**，按代价从小到大排列。这就需要 **K 最短路径（K-shortest paths）** 算法。

## 5. Yen 算法：一条一条「抠」出候选

BravoFinder 用 **Yen 算法** 求 K 最短路（`yen_kshortest.cc`）。思路很直观：

1. 先用 A* 找出**第 1 条**（最短的），放进「已接受」集合。
2. 想找第 2 条，就沿着第 1 条路径上的每个点做「分岔尝试」：
   - 在某个点（叫 **spur node，分岔点**）之前照抄第 1 条（这段叫 **root，根路径**），
   - 从分岔点开始，**禁止**再走第 1 条用过的那条边，强迫它另走一条，用 A* 搜到终点，
   - 把「根路径 + 新分岔段」拼成一条**候选**，扔进候选池。
3. 从候选池里挑代价最小的作为第 2 条，接受它。
4. 重复，直到凑够 K 条（或没有更多不同的路了）。

直觉：**每一条新路都是从已有路的某个点「拐个弯」得到的**，候选池里始终留着所有可能的拐法，每次取最便宜的。这样保证按代价顺序、一条不漏地产出前 K 条。

> Yen 在大图上会重复很多分岔搜索，BravoFinder 做了两项优化（**heuristic 记忆化** + **Lawler 优化**）把 k=10 的查询提速约 2.5×，同时保证结果一字不差。原理与正确性论证见 [yen-lawler-optimization.zh-CN.md](yen-lawler-optimization.zh-CN.md)。

## 6. BravoFinder 的两点特别之处

上面是教科书版本。BravoFinder 的实际用法有两处不同，单独有专文，这里先点名：

- **多源多汇**：一个机场通过 SID/STAR 可以在**多个**衔接点接入航路网，起点和终点都不是单一顶点，而是一组带「引导距离」的候选点。BravoFinder 的 A*/Yen 是**多源多汇**版本，能在不同衔接点之间择优。见 [procedure-modeling.zh-CN.md](procedure-modeling.zh-CN.md)。
- **带约束**：边不是只有长度，还带方向、高低空、高度限制。搜索时这些约束作为**过滤器 + 软代价**介入。见 [compliant-routing.zh-CN.md](compliant-routing.zh-CN.md)。

## 7. 一句话串起来

> 把空域建成**图** → 用 **A\***（单位球弦长启发，admissible 下界保证最优）找最短路 → 用 **Yen** 抠出 **前 K 条**候选 → 全程让**航空约束**参与、让机场靠**真实程序**接入。

这就是 BravoFinder 找出一条航路的完整链条。想深入某一环，接着读对应专题即可。
